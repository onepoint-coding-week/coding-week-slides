En semaine 1, ils ont utilisé git sur leur machine. Aujourd'hui, on travaille à plusieurs sur un dépôt distant, comme toute la semaine. Ce qui est vraiment nouveau pour eux : le fork, la pull request, et surtout la revue en ligne.

Why do we need to know the basics?

  • It's how software is really built.
  • It makes teamwork possible.
  • Code review builds quality and learning (find bugs early, share good ideas…)
  • Conflicts stop being scary and become manageable
  • History and safety: everything is recorded, can be explained and can be undone.

The highway to the main branch

All week, this is how your code reaches the project.

  1. Fork: your own copy, on GitHub
  2. Clone: your fork, on your laptop
  3. Branch: your draft, never main
  4. Push: commit, then send it to your fork
  5. Pull request: ask to bring it into main
  6. Review: someone else reads it
  7. Merge: it's in main, for everyone

Points à dire en tapant :

  • On clone SON fork, pas le dépôt de la salle : l'adresse contient son propre login GitHub. Sinon, le push sera refusé.
  • Au premier push, git demande de se connecter à GitHub. Le dire, sans le montrer : une fenêtre propose de se connecter par le navigateur ; si git demande un mot de passe, c'est le Personal Access Token créé avant le lundi, pas le mot de passe GitHub. Git le retient ensuite.

  • « alice » est un exemple : chacun met son propre login.

Steps 5 to 7: on GitHub

The review is the new part: read the code, say something useful.

  1. Open your pull request: On your fork, click Compare & pull request. Check it goes to the room's repository, main. A clear title, then Create.
  2. Review your neighbour's: Open their pull request, tab Files changed. Click + on a line, leave a comment. A question or an idea, not just "OK".
  3. Reply, then merge: Answer the comments you got. Once it's approved, it gets merged. Your file is now in main.

Minutage : 3:00 (cumul 9:00).

En direct, seulement l'étape 5 : après le push, GitHub affiche sur le fork un bandeau « Compare & pull request ». Cliquer, vérifier en haut que la pull request va bien vers le dépôt de la salle, branche main. Un titre clair, une phrase de description, Create pull request.

Les étapes 6 et 7 se montrent sur la slide, sans les faire :

  • Côté relecteur : l'onglet Files changed, le « + » qui apparaît au survol d'une ligne, un commentaire. Un commentaire obligatoire par personne. Un « OK » ne compte pas : une question, une remarque, une idée.
  • L'auteur répond aux commentaires, puis la pull request est fusionnée. Qui fusionne : le préciser à l'oral, selon l'organisation de la salle.

La relecture se fait entre voisins : chacun relit la pull request de son voisin de gauche, par exemple. Le dire, sinon tout le monde relit la même.

Si le temps manque, ne pas sacrifier la revue : c'est la vraie nouveauté.

So, what happened?

Git merges changes on its own, as long as they touch different lines.

README.md, line 2 This is going to be a fun week.
merge-me-first This is going to be an amazing week, merge me first! Merged first
conflict-here-I-come This is going to be a legendary week, conflict here I come! Conflict

merge-me-first is in main. Git can't guess if conflict-here-I-come should replace it, so it asks.

Minutage : 1:00 (cumul 1:15).

Montrer la pull request merge-me-first, déjà fusionnée. Ouvrir conflict-here-I-come : GitHub affiche « This branch has conflicts that must be resolved ». Le bouton Merge est grisé.

L'expliquer simplement : les deux ont changé la même ligne, et git ne sait pas laquelle garder. Alors il pose la question, et c'est l'auteur de la deuxième pull request qui y répond. Personne n'a fait de faute.

Let's fix it on GitHub

On conflict-here-I-come, click Resolve conflicts.


<<<<<<< conflict-here-I-come
This is going to be a legendary week, conflict here I come!
=======
This is going to be an amazing week, merge me first!
>>>>>>> main

Keep one line, or a mix of both:


This is going to be an amazing, legendary week!
  1. Click Resolve conflicts on the pull request.
  2. Keep the line you want and delete the <<<, === and >>> markers.
  3. Click Mark as resolved, then Commit merge. It can be merged again.

Minutage : 2:00 (cumul 3:15).

En direct, sur la pull request conflict-here-I-come :

  • Cliquer sur « Resolve conflicts ». GitHub ouvre le fichier avec les deux versions de la ligne, entre les marques <<<<<<<, ======= et >>>>>>> : en haut celle de conflict-here-I-come, en bas celle déjà dans main.
  • Demander à la salle laquelle garder, laisser proposer quelques secondes.
  • Écrire un mélange des deux, par exemple « This is going to be an amazing, legendary week! », et effacer les trois marques.
  • « Mark as resolved », puis « Commit merge ». Le conflit disparaît, la pull request peut de nouveau être fusionnée.

Si GitHub ne propose pas de résoudre dans le navigateur (conflit trop compliqué) : cette semaine, appeler un encadrant, qui le fera avec eux.

On the real project

Between teams No conflict possible: each team only changes its own folder, features/team_XX/.
Inside your team Two of you edit the same lines of service.py? That's a conflict, fixed like today.
Fewer conflicts Keep pull requests small and merge them soon. Tell each other who's on which file.

Minutage : 1:00 (cumul 4:15).

Aller vite. Sur le vrai projet, chaque équipe ne modifie que son dossier features/team_XX/ : deux équipes ne peuvent pas entrer en conflit. Les conflits arriveront à l'intérieur d'une équipe, quand deux personnes touchent les mêmes lignes du même fichier, typiquement service.py.

Deux habitudes suffisent presque toujours : de petites pull requests, fusionnées vite, et se dire dans l'équipe qui travaille sur quel fichier.
